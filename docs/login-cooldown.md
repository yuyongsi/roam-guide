# 登录失败冷却

登录失败保护保存在当前服务进程内，不更改账号状态、数据库或永久封禁。服务重启后记录清空；多进程部署时各进程独立计数，不适合作为跨实例的集中限流。登录验证在进程内串行执行，其他接口不受此锁影响。站点作为本地单进程运行时，以连接的 `getRemoteAddr()` 作为来源，不读取 `X-Forwarded-For` 等头。反向代理部署时，该地址可能是代理地址，多个用户会共享来源额度；需要配套可信代理方案后才能改变来源判定。

用户名先按原登录接口去除两端空白，再按 SQLite NOCASE 的行为仅折叠 ASCII 大写字母。相同来源与用户名组合在最近 10 分钟内连续失败 5 次，第 5 次开始冷却 60 秒；同一来源在 10 分钟内累计失败 30 次也冷却 60 秒，包含不同用户名。不存在的用户名与密码错误使用相同提示和计数；正确密码但账号已封禁仍按原有封禁规则处理。成功登录清除对应组合的失败计数，但不清除来源累计数。冷却中的尝试即使密码正确也被拒绝，不延长冷却；触发冷却时该阈值的失败队列清空，冷却结束后可重新尝试。其他失败记录按滑动窗口过期。

接口返回 HTTP 429，JSON 保留 `status`、`code`、`message`、`request_id`，并提供 `code: LOGIN_COOLDOWN`、正整数 `retry_after_seconds` 和 `cooldown_scope`（`pair` 或 `source`），响应头 `Retry-After` 与秒数一致。页面按收到的作用范围显示倒计时；刷新和更换会话无法绕过服务端限制。倒计时仅作辅助，服务端判断为准。

条目总容量为 10000（来源和组合各计一个），每次登录检查按时间清理失效条目。容量满时无法为新来源或组合保留记录，返回 503，不驱逐有效记录，避免借容量压力清除正在冷却的条目。临时计数只存在内存，不向日志或数据库写入原始密码、用户名或来源地址。若需要跨进程保护，应另行设计受信任的共享限流服务。

## 本次验证

2026-10-27 在独立数据库副本及 8832 服务上完成 Java 核心与并发测试、Node 页面源码测试、真实 HTTP 冷却测试（实际等待 61 秒）和浏览器交互检查。既有 15 组 456 项回归，以及表单、错误提示、打印与错误契约检查通过。正式数据库不参与错误登录测试。
