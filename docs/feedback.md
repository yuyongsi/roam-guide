# 反馈与评论举报

用户可以从景点、攻略、目的地、美食、社区帖子和公开路线详情反馈问题；攻略评论与社区评论提供举报入口。页尾的意见反馈入口会带入当前受支持页面。登录前进入反馈会保留来源，登录后显示关联内容。

反馈保留“内容纠错、功能建议、使用问题”三种分类。举报作为内容纠错进入相同处理流程，仅提交人和管理员可见；不自动下架被举报内容，也不向被举报人发送举报详情。

## 关联内容

服务器按规范站内路径查找当前公开资源，并保存标题与评论摘要快照。摘要最多 200 个 UTF-16 单元，边界处保持完整字符。客户端传入的标题和摘要不作为依据。评论必须属于路径指定的攻略或帖子，父内容及所在城市需要满足相应公开条件。

支持具体内容路径及规范评论锚点，例如 `/food/5`、`/community/post/312#comment-49`。一般页面使用明确白名单；不接受外链、任意查询参数、编码路径、私有行程编号和后台路径。由私人行程页进入通用反馈时，只关联“我的行程”入口，不携带私有行程编号或正文。

手动修改关联路径后，旧标题卡立即清除，可点击“核对关联页面”取得新信息。失败时保留反馈正文；移除关联只清除路径与关联卡，仍可提交普通反馈。提交时服务器再次验证关联资源。

目标下架或评论删除后，已有反馈保留原快照，并显示原内容当前不可用，不再提供失效跳转。查询上下文不能获取未公开内容的新标题或正文。

## 管理与通知

管理员可按反馈内容、用户、类型、关联标题或评论摘要搜索并分页处理。标记已处理需要填写说明；用户在反馈记录中查看结果，消息中心收到进展通知。回复、通知和成功审计记录处于同一事务；重复保存相同结果不重复发送通知。

## 初始化与检查

`feedback` 表增加 `page_title`、`target_excerpt` 两个默认空文本字段。启动时只补充已有表缺失的列，旧反馈和其他数据不重写；独立全量 schema 包含新列，固定演示数据库保持不变。

`tests/verify_feedback_context.py` 只允许显式配置的本机非 8818 实例及项目 `work/` 下的数据库，检查公开性、评论归属、快照可信性、用户隔离、通知与回滚；`tests/verify_feedback_frontend.js` 调用实际渲染与路径函数检查转义和跳转安全。投稿表单行为由 `tests/verify_contribution_form.cjs` 检查，并配合真实浏览器操作验收。
